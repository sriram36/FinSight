# FinSight AI MVP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the complete evidence-grounded personal finance decision support application and research evaluation lab from the PRD, starting with an end-to-end vertical slice (CSV import → profile → System C recommendation → claim verification).

**Architecture:** A decoupled full-stack architecture where the Next.js frontend handles responsive, accessible UI states and user interactions, while a Python FastAPI backend serves as the single source of truth for deterministic financial arithmetic, database persistence, recommendation orchestration (Systems A, B, B-ablation, C), and strict evidence verification.

**Tech Stack:** Next.js 16 (App Router, TypeScript, Tailwind CSS, Base UI, Lucide), FastAPI (Python 3.12+, Pydantic v2, SQLAlchemy 2, Alembic, SQLite/PostgreSQL), scikit-learn/pandas/numpy, pytest, and optional Azure OpenAI Responses API with offline mock fallback.

**Spec:** [FinSight_AI_Complete_PRD.md](file:///d:/FinSight/FinSight_AI_Complete_PRD.md)

## Global Constraints

- **Single Source of Truth:** All financial arithmetic (totals, daily pace, period-normalized baselines, percentage deviations, affordability, goal feasibility) must be calculated deterministically by the backend. The LLM is never the source of truth for numbers.
- **Strict Evidence Verification:** No numeric claim generated by an LLM in System C may be displayed as verified unless checked against backend-computed evidence values within specified rounding tolerances.
- **Protected Category Invariant:** A category marked as protected by the user cannot be proposed as a reduction target by any recommendation engine.
- **Mode Separation:** Personal Finance Mode (user uploaded CSV/manual entry) and Research Lab Mode (synthetic PersonaLedger dataset) are strictly isolated. Synthetic benchmarks must never be displayed as real personal finances.
- **Graceful LLM Fallback:** External LLM unavailability, timeouts, or schema validation failures must fall back safely to deterministic rule advice or safe notices without crashing non-AI features.
- **Zero Raw Secret Exposure:** API keys and credentials reside exclusively in server-side environment variables; never exposed to the client bundle or git.
- **Accessible UI:** WCAG 2.1 AA compliance (4.5:1 contrast, touch targets >= 44x44px, keyboard navigation, text alternatives for charts).

## Review Focus

1. **Zero-Baseline and Unequal-Window Division:** When calculating baseline pace or percentage deviation, categories with zero historical baseline or unequal observation windows must not cause `ZeroDivisionError` or produce misleading "+9999%" spikes.
2. **CSV Format and Sign Discrepancies:** Bank statements vary in header names, date formats, and sign conventions; negative spending or ambiguous credit/debit columns must be cleanly normalized into explicit transaction directions (`spending`, `income`, `transfer`, `refund`, `payment`).
3. **Temporal Leakage in Research Holdouts:** In Research Lab mode, holdout-period transactions (the final 30 days) must never be accessible to the baseline profile generation or recommendation prompt.
4. **LLM Hallucination and Format Drift:** Malformed JSON or invented monetary values in LLM responses must trigger bounded retry or fallback to System A rather than showing unverified figures.
5. **Cross-User Data Isolation:** Every query and mutation on transactions, profiles, goals, and recommendations must filter strictly by the authenticated `user_id`.

### Phase 2: Deterministic Calculation Engine (Vertical Slice Part 2)

#### Task 5: Profile Spending Calculation Engine & Period Normalization
**Files:**
- Create: `backend/services/profile_service.py`
- Create: `backend/schemas/profile.py`
- Create: `backend/routers/profile.py`
- Test: `backend/tests/test_profile_math.py`

**Interfaces:**
- Consumes: User transactions within a historical baseline window ($D_b$ days) and recent window ($D_r$ days).
- Produces: Category profile with `baseline_daily_pace`, `recent_daily_pace`, `normalized_baseline`, `percentage_deviation`, `is_low_baseline`, and total spending metrics.
- Mathematical Rule:
  $$\text{baseline\_pace} = \frac{B}{D_b}, \quad \text{recent\_pace} = \frac{R}{D_r}$$
  $$\text{normalized\_baseline} = \text{baseline\_pace} \times D_r$$
  $$\text{deviation} = \frac{R - \text{normalized\_baseline}}{\text{normalized\_baseline}} \times 100 \quad (\text{if } B \ge \text{threshold})$$
